# DropKnow 产品页面体验打磨方案

> 适用仓库：`/Users/cc/Desktop/DropKnow`
> 目标：把当前页面从“能展示骨架”推进到“状态可信、层次清楚、动作顺手、风格统一”
> 适用范围：`MenuBar`、`QuickPanel`、`Document Detail`、`Settings`、卡片与浮层

---

# 1. 先定原则：这次不是先做美化，而是先做体验闭环

产品页面体验打磨的顺序必须是：

1. 先补状态
2. 再改信息层级
3. 再补动作和边界态
4. 最后做视觉统一

原因很简单：DropKnow 的核心不是“页面好不好看”，而是用户能不能快速判断：

- 这是什么文件
- 现在处理到哪一步了
- 我下一步该点什么
- 为什么这里卡住了

---

# 2. 当前页面真实短板

结合现有仓库 UI 骨架，主要问题是：

1. `DocumentDetailView` 已经有状态分支，但页面结构还偏“把信息堆出来”
2. `QuickPanelSceneView` 还接近一个输入框 + 按钮 + 文本结果
3. `SettingsView` 还是偏占位表单，不像能力管理页
4. `MenuBarSceneView` 还在“最近文件 / 重要提醒”二选一，没有稳定顶层状态区
5. loading、blocked、failed、partial success 没有在所有页面保持统一表达

---

# 3. 页面体验打磨总目标

## 3.1 用户感知目标

用户第一次使用时，应当做到：

1. 打开菜单栏，马上知道最近有没有重要事情
2. 打开详情页，3 秒内看懂“一句话摘要 + 要做什么”
3. 用 QuickPanel 时，知道自己是在“搜索”还是“问答”
4. 被隐私门禁、额度、权限卡住时，知道为什么卡住，以及下一步去哪处理

## 3.2 工程落地目标

页面改造必须落在现有结构内：

- Scene：`/Users/cc/Desktop/DropKnow/DropKnow/App/Scenes/`
- View：`/Users/cc/Desktop/DropKnow/DropKnow/Views/`
- ViewModel：`/Users/cc/Desktop/DropKnow/DropKnow/Features/*/ViewModels/`
- 设计真集：`/Users/cc/Desktop/DropKnow/落知_SwiftUI组件规格与页面实现指南.md`
- 状态真集：`/Users/cc/Desktop/DropKnow/docs/ViewModel 状态映射表.md`

# 4. 打磨原则

## 4.1 状态优先于视觉

所有页面必须先回答“状态是什么”，再回答“长什么样”。

优先统一的状态包括：

- `loading`
- `processing`
- `blocked`
- `failed`
- `partial success`
- `ready`
- `empty`

## 4.2 一个页面只突出一个主任务

- `MenuBar`：快速扫一眼最近情况
- `QuickPanel`：快速搜、快速问
- `Document Detail`：看懂文件并处理动作
- `Settings`：理解能力边界并修改设置

## 4.3 同一状态在不同页面必须同口径

例如：

- “处理中”不能在一个页面叫“处理中”，另一个页面叫“分析中”
- “被阻断”不能只给红字，不解释原因
- “部分成功”必须明确哪一步成功、哪一步失败

## 4.4 先修最伤信任感的边界态

体验最容易崩的不是 happy path，而是：

1. 摘要成功但事件失败
2. 文件被隐私门禁挡住
3. 日历不可写入
4. 搜索无结果
5. provider 失败但页面只显示空白

# 5. 页面级打磨方案

## 5.1 Document Detail

### 为什么先做它

它是信息最完整、状态最复杂、最适合沉淀页面规范的地方。

### 当前问题

1. 当前结构主要是 `SummaryCard + Evidence + Buttons + Events` 顺序堆叠
2. “摘要阅读”和“事件处理”还没有形成明显主次
3. blocked / failed / waitingUserConfirmation 虽然有分支，但没有统一页面骨架

### 打磨目标

进入详情后，用户应当先看到：

1. 这是什么文件
2. 一句话摘要
3. 要不要立刻处理
4. 如果卡住，是为什么

### 推荐结构

1. `DetailHeader`
2. `SummaryHeroBlock`
3. `ActionRequiredSection`
4. `EvidenceSnippetSection`
5. `EventCandidatesSection`
6. `InspectorColumn`

### 具体步骤

1. 先把 `DocumentDetailViewModel.State` 对齐到文档真集
2. 明确 `partial success` 表达
   这里建议至少支持“摘要成功、事件失败”这一路径
3. 在 `DocumentDetailView` 中固定页面骨架
   即使 blocked/failed，也不要退化成只有几行文字
4. 把“打开原文件”“重新解析”“加入日历”“忽略”拉出主次
5. 让 `SummaryHeroBlock` 成为视觉焦点
6. 事件区域按钮化，不只展示文本

### 验收口径

1. 3 秒内能看到一句话摘要
2. 有动作时，主按钮明显
3. 被阻断时，知道原因和下一步
4. 部分成功时，不会被当成全失败

## 5.2 MenuBar

### 当前问题

1. 当前主要是 tab 切换，没有顶层稳定状态区
2. 最近文件和重要提醒缺少主次分层
3. 空态、处理中、异常态表达不够强

### 打磨目标

用户打开 5 秒内看懂：

1. 最近是否有重要提醒
2. 当前有没有文件在处理
3. 最近理解出来了什么

### 推荐结构

1. `StatusHeader`
2. `ImportantReminderSection`
3. `RecentDocumentsSection`
4. `QuickActionsSection`

### 具体步骤

1. 固定顶部 `StatusHeader`
   显示 watcher 状态、最近处理时间、配额摘要
2. 重要提醒永远在最近文件上方
3. 最近文件只保留 3 到 5 条
4. 每条 recent row 都带统一状态 badge
5. 底部提供快捷入口
   包括搜索、设置、打开详情

### 验收口径

1. 用户一眼知道哪个最重要
2. 提醒和普通文件不会混成一个平面列表
3. 处理中时不会像“没反应”

## 5.3 QuickPanel

### 当前问题

1. 现在更像“输入框 + 搜索按钮 + 文本结果”
2. 搜索和问答没有体验区分
3. 无结果、额度受限、provider 失败缺少明确提示

### 打磨目标

把它做成“轻量问题入口”，而不是只有一个文本框。

### 推荐结构

1. `QueryInputBar`
2. `ModeSegmentedControl`
3. `SuggestionList`
4. `SearchResultList` 或 `AnswerResultView`
5. `BottomContextBar`

### 具体步骤

1. 先补 `SearchViewModel` 状态机
   建议至少有：`idle`、`retrieving`、`assembling`、`answering`、`noResult`、`blocked`、`failed`
2. 明确两种模式
   搜索看“结果列表”
   问答看“答案 + 证据”
3. 默认态显示推荐问题或最近搜索
4. 无结果要解释“没搜到”，不是空白
5. 底部显示当前模式、额度、打开详情动作

### 验收口径

1. 不用学习就知道这里可以搜和问
2. 搜索结果和问答结果长得不一样
3. 失败、无结果、被限制都能解释

## 5.4 Settings

### 当前问题

1. 当前 `SettingsView` 更像功能占位
2. 目录、权限、日历、订阅、诊断没有清楚分区
3. 用户不知道某个设置会影响什么

### 打磨目标

把 Settings 从“表单页”提升为“能力管理页”。

### 推荐结构

1. `DirectorySettingsSection`
2. `PrivacySettingsSection`
3. `CalendarSettingsSection`
4. `SubscriptionAndQuotaSection`
5. `DiagnosticsSection`

### 具体步骤

1. 目录区说明当前监听目录和权限状态
2. 隐私区说明高风险文件策略和最近门禁决策
3. 日历区说明权限状态、可写条件、失败原因
4. 订阅区说明免费版限制和剩余额度
5. 诊断区展示最近错误和 provider 状态

### 验收口径

1. 用户 30 秒内能找到目录授权和日历限制原因
2. 订阅能力边界明确，不靠猜
3. 设置项能解释后果，不是裸开关

## 5.5 卡片与浮层

### 当前问题

1. 普通卡片和重要事件卡片差异不够大
2. 成功、警示、失败、阻断缺少稳定样式规则

### 打磨目标

让用户看到卡片就知道：

1. 这是普通信息，还是需要马上处理
2. 是成功完成，还是停在某个风险点

### 具体步骤

1. 普通文件卡片突出文件名和一句话摘要
2. 事件卡片突出时间、地点、主按钮
3. 阻断和失败态不要沿用成功态颜色
4. 浮层文案统一使用“原因 + 下一步”

### 验收口径

1. 普通卡片与事件卡片一眼区分
2. 风险态不会误导成成功态

# 6. 统一视觉语言

## 6.1 语义色

只保留少量语义色：

- 中性：正文、说明、边框
- 重点：高优先级事件
- 成功：完成、已入历
- 警示：需确认、额度不足、失败、阻断

## 6.2 字体层级

统一成五层就够：

1. 页面标题
2. 一句话摘要
3. 正文/重点
4. 元信息
5. 状态提示

## 6.3 间距与密度

- MenuBar：紧凑，但层次清楚
- Detail：留白明显，主内容突出
- QuickPanel：输入和结果之间要有呼吸感
- Settings：分组比密度更重要

---

# 7. 推荐推进顺序

不要所有页面一起动，建议严格按这个顺序：

1. `Document Detail`
2. `MenuBar`
3. `QuickPanel`
4. `Settings`
5. `卡片/浮层`

原因：

1. `Document Detail` 最适合先沉淀状态真集和页面结构
2. `MenuBar` 是最高频入口，第二优先
3. `QuickPanel` 依赖搜索真实闭环，适合在结构先定后逐步接真结果
4. `Settings` 最后收口能力说明和诊断

# 9. 每轮都要检查什么

## 文档检查

1. 状态命名是否和真集一致
2. 组件 Props 改了没同步 UI 真集
3. ViewModel 状态改了没同步状态映射表

## UI 检查

1. loading 不应只是一句文字敷衍
2. blocked 必须解释原因
3. failed 必须给下一步
4. partial success 不能伪装成全失败
5. 主按钮只能有一个最强焦点

## 验收检查

1. 菜单栏能一眼看出重点
2. 详情页能快速看懂是什么、要做什么
3. QuickPanel 不再只是文本框
4. Settings 能解释能力边界和失败原因
5. 状态词、按钮词、样式口径一致

# 10. Codex 执行规则

## 10.1 页面改造顺序

1. 只按本文档的顺序推进
2. 一次只改一个页面阶段
3. 先改状态文档，再改 ViewModel，再改 View/Scene
4. 未完成当前页面验收前，不跳去下一个页面

## 10.2 文档同步规则

只要出现以下任一情况，就必须同步文档：

1. 改页面状态：同步 `/Users/cc/Desktop/DropKnow/docs/ViewModel 状态映射表.md`
2. 改组件 Props 或页面结构：同步 `/Users/cc/Desktop/DropKnow/落知_SwiftUI组件规格与页面实现指南.md`
3. 改能力边界文案：同步相关真集或实施文档，保证状态词一致

## 10.3 每轮交付格式

每一轮页面打磨结束后，必须输出：

1. 本轮页面
2. 状态改动
3. 结构改动
4. 修改文件
5. 验收结果
6. 剩余体验问题

# 11. 最后一句话

页面体验打磨不是“统一圆角和颜色”这么简单，真正要先打磨的是：

- 用户是否看得懂
- 状态是否可信
- 动作是否顺手
- 被卡住时是否知道下一步

只要先把这四件事做稳，视觉统一会自然容易很多。
